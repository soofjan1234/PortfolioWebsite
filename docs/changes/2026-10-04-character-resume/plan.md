## 阶段一：得到可编辑的真实人物 GLB

输入为已确认的头像与黑发正面 v5；输出为保存到 `assets/model/hou-base-v1.glb` 的真实基础模型及彩色版 `hou-textured-v1.glb`、结构报告。最新造型参考为 `assets/character-front-v5-unified.png`。上述路径相对本主题目录。

1. 从四视图准备独立正面参考，通过已授权的 Meshy 图生 3D 上传流程使用 Meshy 6 Lite 生成一份初稿，记录页面显示的点数和模型版本。不购买套餐或追加额度。
2. 下载 GLB，保存来源、使用的输入、许可和生成参数到 `assets/model/source.md`。在需要署名的免费许可下保留 Meshy 署名信息。
3. 新建 `scripts/validate-character-model.mjs` 和 `scripts/validate-character-model.test.mjs`。先运行 `node --test scripts/validate-character-model.test.mjs`，验证缺少校验实现时按预期失败；用真实格式的最小 GLB 固定头部、长度、节点和动画检查的公共行为。
4. 实现 GLB 基础结构报告及就绪契约检查。基础模式检查容器、JSON、场景、网格、材质和纹理依赖；就绪模式额外检查眼球、相机、`CameraAction` 与对焦节点。不能让基础模式的通过掩盖就绪节点缺失。
5. 运行目标测试，再执行 `node scripts/validate-character-model.mjs docs/changes/2026-10-04-character-resume/assets/model/hou-base-v1.glb --stage=base`。基础模型应可解析，缺少相机和独立眼球应在报告中明确列出。输出数量、关键字段与 SHA-256，不打印大段网格或纹理数据。
6. 在模型预览中检查正面与侧面识别度、眼镜、头发、肩颈和破面，保存截图证据。基础质量不足则记录实际差异，不能直接进入成品验收。

前置条件：设计与上传授权已确认，Meshy 登录可用，并具备 GLB 下载权限。

校验器最小输入/输出已经冻结：`inspectCharacterModel(bytes, { stage, resumeCount })` 输入 GLB 字节、`base` 或 `ready` 阶段以及正整数履历数；输出通过状态、字节数、SHA-256、节点/网格/纹理等数量、官方结构校验错误数与首个问题，以及单独的交互契约缺项。CLI 参数为 `文件.glb --stage=base|ready --resume-count=N`，通过退出码为 0，失败为 1。结构校验使用 Khronos 官方 `gltf-validator`，拒绝外部资源依赖。就绪检查不能代替外观、眼球旋转中心和关键镜头的实际预览验收。

## 阶段二：模型可以驱动原站交互

前置条件：阶段一基础模型通过结构与外观检查。

本阶段最小契约已冻结：精修脚本输入彩色 GLB 与 `src/data/character-scene.json` 的履历顺序、24 fps / 50 帧镜头约定；输出可编辑 `.blend`、自包含 `public/models/me.glb`、精简结构报告及正面/侧面/眼球转动证据。当前沿用网站的两项履历（广州大学、深圳 Go 后端工作），因此需五个焦点。脚本保留原始输入，通过纹理与空间区域拆分头发、衣服、眼镜和眼球；眼球采用中心局部坐标，重建完整转动体积，防止转动后出现原来的瞳孔。头发先移除细碎形体和过深凹槽，须比较修整前后的轮廓，不以节点存在代替外观验收。可编辑源与网页成品都保留来源署名。

1. 在 `.gitignore` 加入 `.codex*` 与 `.gocache/`，将本任务的建模运行环境放在忽略目录；使用可靠来源的 Blender 或其官方 Python 模块。
2. 保存精修脚本到 `scripts/prepare-character-scene.py`；保存可继续编辑的建模场景和输出信息到主题的 `assets/model/`。以已确认的最小模型契约补齐或修复眼球、眼镜、镜片、材质、相机轨道和焦点。
3. 将网页成品模型导出到 `public/models/me.glb`。先运行就绪检查，看到当前基础模型因契约节点缺失而失败；补齐之后运行同一检查达到目标 GREEN。
4. 渲染正面、侧面与关键特写，检查眼球旋转中心和镜片遮挡；再次运行完整模型校验测试。保留真实结果，避免仅靠节点命名宣称互动可用。

模型阶段及 [人物质感联合精修实施计划](plan/character-quality.md) 已完成。用户确认收尾后，已将最后的精修版本发布为 `public/models/me.glb`；第一版保留在 `assets/model/quality-refinement/baseline.glb`。该正式模型已接入阶段三主页，网页进度以状态表和 [验收记录](home-verification.md) 为准。

## 阶段三：网页完整浏览与横向末尾栏目

前置条件：阶段二有通过就绪检查的模型。

1. 准备统一的内容与焦点节点定义，首页装配固定场景、简介、履历、Tech Hub 与末尾作品。适配参考站代码时保留 MIT 来源说明。根据用户明确修正，构图、绿色背景、颗粒、磨砂和深色展板沿用参考站视觉，人物和内容使用自己的版本。
2. 先以 Vitest 验证滚动阶段、正反向横向进度、触屏分支、减少动态效果和加载失败保留内容，再实现对应行为。
3. 用现有 Markdown 数据支持 Tech Hub 文章访问；保持现有 `/projects` 入口可访问，避免直接丢失已有知识内容。
4. 执行目标 Vitest，再运行相关完整测试与 `npm run build`。通过浏览器在桌面和窄屏检查完整浏览、眼球互动、景深、横向栏目退出与链接，并保存截图。

验证命令和最终文件边界在进入各阶段时按实际代码接缝补齐；若发现需要改变已确认模型契约，则先更新设计并确认该变化。

阶段三继续使用已确认的页面结构和模型契约；先接入首屏人物、统一内容与滚动镜头，再实现作品和横向 Tech Hub，最后验证完整浏览与失败降级。人物制作不再作为网页实施的前置待办。

### 阶段三最小契约（编码前冻结）

- 输入：`character-scene.json` 的履历顺序、焦点和 24 fps / 50 帧配置，以及各 HTML 锚点的文档坐标。履历正文只补充到该配置，不另设节点顺序。
- 镜头输出：纯函数按滚动位置返回帧数、阶段、相邻焦点与插值比例；首屏 0 帧，每个后续节点递增 50 帧，正反向结果一致，越界钳位。GLB 的 `CameraAction` 以帧数 / fps 定位，景深跟随相同焦点。
- 横向输出：桌面栏目高度为视口高度加轨道溢出宽度，纵向滚动与横向偏移保持 1:1；触屏、窄屏或减少动态效果采用原生左右滚动与前后按钮，不拦截页面滚轮。
- 阅读输出：HTML 简介、两项履历、六项作品与三类 Tech Hub 始终挂载。模型超时、下载/解析错误、WebGL 初始化失败及上下文丢失切换为静态人物；减少动态效果不加载 3D。分类文章复用现有 Markdown 文件，失败显示重试和 `/projects` 入口。
- 文件边界：`src/pages/Home.jsx`、主页专用样式、`src/components/home/`、`src/lib/home-scroll.js`、`src/data/`；App 仅调整主页导航、锚点及无障碍入口。保留现有 `/projects` 与 `/experience`。
- 验证：先运行新增 Vitest 获得预期 RED，再运行目标 GREEN；最后运行全部主页 Vitest、现有模型契约测试、正式 GLB 校验及生产构建。浏览器检查桌面首屏/各履历/作品/Tech Hub/正反向退出、手机触屏与窄屏、加载失败、减少动态效果、文章/项目/联系入口，并保存截图及精简报告。
